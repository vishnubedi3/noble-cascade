# Repository Governance — Noble Cascade

This document describes the actual repository: what is enforced by machinery,
what requires a human, and how a change becomes a release. Anything here that
is not enforced is marked MANUAL. See also `docs/maintainer-security-checklist.md`.

## 1. Branch model

- `main` is the only long-lived branch and the only release source.
  (ENFORCED in tooling: release provenance binds `RELEASE.json` to the `main`
  commit it was built from; branch deletion/push policy itself is MANUAL —
  owner must set branch protection, see the maintainer checklist.)
- Feature work happens on short-lived branches, merged via pull request.
- Force pushes and branch deletion of `main` are prohibited by policy; the
  mechanical control is owner-level branch protection (MANUAL).

## 2. Change pipeline (the security boundary)

```
Change -> Review -> CI -> Security verification -> Governance certification
  -> Merge -> Release
```

No substantive change should bypass this sequence accidentally. The links are:

| Link | Mechanism | Status |
|---|---|---|
| Review | PR required + CODEOWNERS for security-critical paths | MANUAL (branch protection + teams) |
| CI | `main.yml` + `ci-hardened.yml` required checks | MANUAL (required-check config) + ENFORCED (checks themselves fail closed) |
| Security verification | bandit, CodeQL, dependency-review, secret scan, pip-audit | ENFORCED (in CI) |
| Governance certification | `noble certify` == CERTIFIED, baseline + workflow audit | ENFORCED (CI fails otherwise) |
| Merge | up-to-date branch, stale-approval invalidation | MANUAL (branch protection) |
| Release | tag -> artifacts -> attestation binding | ENFORCED (`noble release --verify`) |

## 3. CI model

Two verification levels, explicitly separated:

- **Local (fast, development):** `main.yml` — lint, format, type-check, tests,
  bandit, secret scan, pip-audit, `noble doctor`. Equivalent local command:
  `ruff check noble tests && ruff format --check noble tests && mypy noble && python -m pytest -q`.
- **Release (complete, governance):** `ci-hardened.yml` — everything above plus
  supply-chain verification, `noble drift`, `noble ledger --verify`,
  `noble audit --verify`, `noble spec --verify`, `noble certify`,
  governance baseline + workflow audit, audit-pack regeneration + offline
  verification, and `./verify-everything.sh` (20 checks).

Release verification is never weakened to make CI faster: `verify-everything.sh`
is the external contract and its check list only grows (exit codes are stable).

## 4. Approval model

- Every PR to `main` needs maintainer review (MANUAL: branch protection).
- Changes matching `.github/security-critical.json` (severity high/critical)
  need the owning domain's review per `.github/CODEOWNERS` (MANUAL until owner
  creates the teams; the classification itself is ENFORCED — `noble governance
  --pr-analysis` computes it deterministically).
- Stale approvals after relevant changes must be invalidated (MANUAL).

## 5. Security model

- The Noble governance kernel (`noble/`) is authoritative for execution
  behavior. GitHub-native systems (CodeQL, dependency-review, secret scanning)
  ADD evidence; "GitHub says safe" never implies "Noble says safe".
- Workflows run with `permissions: contents: read` at top level; extra grants
  are per-job and minimal (`pull-requests: read` for dependency-review,
  `security-events: write` for CodeQL upload). Audited by
  `noble governance --workflow-audit` (ENFORCED in CI).
- All third-party actions pinned to immutable SHAs (ENFORCED in CI: any
  `@vN` moving tag fails the workflow-integrity step).
- Dependabot PRs enter the same pipeline: lockfile change -> audit -> tests ->
  verification -> review -> merge. No bypass path exists in configuration.

## 6. Artifact model

- `release/` — reproducible release bundle (RELEASE.json, SBOMs, PROVENANCE,
  POLICY_HASHES, TEST_RESULTS, SECURITY_SPEC_HASH, WORKER_DIGESTS,
  ATTESTATION.md). Regenerated by `noble release --create`, verified by
  `noble release --verify`.
- `audit-pack/` — independent offline bundle + `verification.sh`.
- CI uploads `noble-release-<sha>` artifacts with 7-day retention (tamper-evident
  naming; content verified by hash, not by filename).

## 7. Evidence model

```
certified source == tagged source == built source == attested source
```

`noble release --verify` proves: certified source is HEAD or an ancestor of
HEAD with no governed file changed since certification (no release drift),
exact tag == stored tag when HEAD is tagged, artifact bytes ==
POLICY_HASHES.json, policy/config/worker hashes == current, attestation
signature valid. Any mismatch fails. Noble attestation (HMAC-SHA256 over
canonical JSON) is the primary chain; GitHub artifact attestations may be
added later as cross-system provenance — never as a replacement.

## 8. Emergency change procedure

Emergency means faster governance, not absent governance. An emergency change
(a security fix that cannot wait for the normal review window) must still
produce, at merge time or within 24h after:

1. actor (who merged)
2. timestamp
3. reason (incident reference, why normal review was skipped)
4. affected files (`git show --name-only`)
5. verification result (`./verify-everything.sh` output attached to the PR)
6. post-change review (a second maintainer approves within 24h; the PR stays
   open until that happens)

Mechanically: the emergency PR still runs the full required-check set — CI
cannot be skipped by label. Only the *human review timing* changes, and the
post-change review is tracked as a MANUAL checklist item.

## 9. Compatibility and deprecation

See `docs/compatibility-policy.md`. Breaking changes to CLI, replay records,
audit records, findings, policies, or release artifacts require explicit
versioning; deprecated interfaces carry introduction version, reason, migration
path, and removal target.

## 10. External auditors

See `docs/external-auditor.md` for the privileged-access-free verification
path: clone -> setup -> verify -> certify -> inspect -> replay -> audit -> release.
